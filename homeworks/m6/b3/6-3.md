# Блок 6.3 — LangGraph: основы

## Что делаем
ReAct-агент из ДЗ Б6.2 (цикл по `max_iterations` с `tool_calls` и `self-reflection`) переписывается на LangGraph 1.0+. Концепция ReAct заново не разбирается — она переводится в orchestration-форму: явный `StateGraph` , типизированный `State` , отдельные узлы для модели и tools, conditional edge с router-функцией. Это инкремент к итоговому дипломному агенту. Граф собирается с заделом на развитие: поверх него позже подключается `AsyncSqliteSaver` / `AsyncPostgresSaver` для checkpointing и `interrupt` для human-in-the-loop, а сам граф может стать одним из subgraph-ов в supervisor-схеме. Чтобы такой переход прошёл без переписывания, в этой работе фиксируются два пути сборки одного и того же агента (кастомный `StateGraph` руками и prebuilt-агент через `langchain.agents.create_agent` ) и сравниваются с реализацией Б6.2 по latency и token usage на тех же 5 задачах.

## Задачи
1. **Установка зависимостей.** В `pyproject.toml` (или `requirements.txt` ) проекта фиксируются: `langgraph>=1.0,<2` , `langchain>=1.0,<2` , `langchain-openai>=1.0` (или `langchain-anthropic>=1.0` — провайдер по выбору для диплома), `langchain-core>=1.0` . Версия проверяется командой `python -c "import langgraph; print(langgraph.__version__)"` — должно быть 1.x. Если в окружении уже стоит старый `langgraph<1.0` , окружение поднимается в чистый venv: API сильно поменялось, mixed-installation даст странные импорты.
2. **State.** В `app/services/agent_graph.py` объявляется `class AgentState(TypedDict)` со следующими полями: `messages: Annotated[list[AnyMessage], add_messages]` (импорт `add_messages` из `langgraph.graph.message` ), `iteration_count: int` (без `Annotated` — reducer по умолчанию replace), `tool_results: Annotated[list[dict], operator.add]` (накопление результатов tools для отчёта и трейсинга). В state не кладутся SDK-клиенты, http-сессии, API-ключи — только сериализуемые данные. Допустимо `class AgentState(MessagesState)` через наследование с добавлением своих полей сверху.
3. **Tools.** Переносятся те же 2–3 tools, которые были в ДЗ Б6.2 (например, `multiply` , `search_knowledge_base` , плюс один доменный — под предметную область диплома). Оформление — через `@tool` -декоратор `langchain_core.tools` с осмысленным docstring (это и есть description для LLM). Описание не дублируется — тот же tool потом пойдёт и в кастомный граф, и в prebuilt.
4. **Nodes.** В `app/services/agent_graph.py` пишутся три узла как чистые async-функции:
   * `async def call_model(state) -> dict` — вызывает `model.bind_tools(tools).ainvoke(state["messages"])` , возвращает `{"messages": [response], "iteration_count": state["iteration_count"] + 1}` .
   * `async def execute_tool(state) -> dict` — берёт `last_message.tool_calls` , находит инструмент по имени ( `{t.name: t for t in TOOLS}` ), вызывает его, оборачивает результат в `ToolMessage(tool_call_id=...)` , добавляет запись в `tool_results` . Если `tool_call["name"]` неизвестен — возвращает ToolMessage с описанием ошибки, не падает.
   * `async def force_finish(state) -> dict` — формирует финальный ответ, если был достигнут `max_iterations` (force-finish), либо просто прокидывает последний AI-message. Этот узел нужен, чтобы граф не уходил «молча» в END.
5. **Router и сборка кастомного StateGraph.** Пишется `def route_after_model(state) -> Literal["execute_tool", "force_finish"]` — детерминированная функция без сайд-эффектов. Логика: если `state["iteration_count"] >= 6` → `"force_finish"` ; если у последнего сообщения есть `tool_calls` → `"execute_tool"` ; иначе → `"force_finish"` .
   Сборка графа: `add_node` для трёх узлов, `add_edge(START, "call_model")` , `add_conditional_edges("call_model", route_after_model, {"execute_tool": "execute_tool", "force_finish": "force_finish"})` , `add_edge("execute_tool", "call_model")` , `add_edge("force_finish", END)` . Компиляция: `custom_graph = builder.compile()` .
6. **Prebuilt-вариант.** В том же файле собирается второй агент через `from langchain.agents import create_agent` (в LangChain 1.0 это рекомендуемый путь; старый `langgraph.prebuilt.create_react_agent` deprecated, но всё ещё работает — при его использовании оставляется комментарий с TODO на миграцию). Передаются те же `model` , `tools` , `system_prompt` . Переменная называется `prebuilt_graph` . Цель шага — иметь два независимо вызываемых runnable, которые решают одну задачу разными путями.
7. **Визуализация графа.** Пишется `scripts/visualize_graph.py` , который импортирует `custom_graph` и `prebuilt_graph` из `app/services/agent_graph.py` , вызывает `graph.get_graph().draw_mermaid()` и сохраняет результат в `docs/agent-graph-custom.mmd` и `docs/agent-graph-prebuilt.mmd` . Дополнительно (опционально) пробуется `draw_mermaid_png()` с сохранением PNG в `docs/agent-graph.png` — если в окружении нет `pyppeteer` / `playwright` , остаётся только `.mmd` . `.mmd` -файл открывается в mermaid.live — схема должна рисоваться и совпадать с ожидаемым представлением.
8. **Бенчмарк Б6.2 vs кастом vs prebuilt.** Берутся те же 5 задач, на которых агент прогонялся в ДЗ Б6.2 (2 простых с одним tool, 2 средних с цепочкой tools — composability, 1 «провокационная» — правильное поведение НЕ вызывать tool вовсе). Пишется `scripts/bench_agents.py` : для каждой задачи и для каждой из трёх реализаций (Б6.2 наивный loop, custom StateGraph, prebuilt) измеряется wall-clock latency ( `time.perf_counter()` ) и суммарный token usage (через `response.usage_metadata` или callback `get_openai_callback()` из `langchain_community.callbacks` — что доступно в провайдере). Усреднение — по 3 прогонам на задачу. Результат — таблица в `docs/agent-graph-report.md` : задача × реализация × latency_ms × prompt_tokens × completion_tokens × total_steps.
9. **Отчёт docs/agent-graph-report.md .** Структура:
   1) Конфигурация (модель, температура, max_iterations, список tools);
   2) Описание state contract (поля, reducers, что хранится и почему именно это);
   3) Описание router-логики и stop conditions;
   4) Mermaid-схема кастомного графа (содержимое agent-graph-custom.mmd вставляется в блок \`\`\`mermaid);
   5) Таблица бенчмарка из шага 8;
   6) Сравнение custom vs prebuilt: что пришлось писать руками, что prebuilt сделал самостоятельно, в каком случае какой путь предпочтительнее;
   7) Один баг, найденный при отладке (например, «забыт add_messages — история перезаписывалась» или «router возвращал bool вместо строки»);
   8) Что блокирует переход к персистентности / чекпойнтингу (например, «нужен thread_id в config — добавлен, но без checkpointer пока no-op»).
10. **Проверка с thread_id (бонус).** В `scripts/bench_agents.py` для кастомного графа передаётся `config={"configurable": {"thread_id": f"bench-{task_id}"}}` . Сейчас, без checkpointer, это no-op — но интерфейс вызова уже совместим с персистентностью, и при подключении `AsyncSqliteSaver` ничего переписывать не придётся.

## Критерии самопроверки
- [ ] `app/services/agent_graph.py` содержит `AgentState` с `messages: Annotated[..., add_messages]` , `iteration_count: int` , `tool_results: Annotated[..., operator.add]` . SDK-клиентов и API-ключей в state нет.
- [ ] Собраны два рабочих графа: `custom_graph` ( `StateGraph` руками с тремя узлами и conditional edge) и `prebuilt_graph` (через `langchain.agents.create_agent` ). Оба отвечают на одну и ту же задачу из шага 8.
- [ ] Router — отдельная функция, читает state, не пишет в него, не делает сетевых вызовов, типизирован через `Literal[...]` .
- [ ] В графе явный stop-кран: `iteration_count >= 6` уводит в `force_finish` , а не в бесконечный цикл. Проверено на задаче, где tool намеренно сломан или возвращает заведомо бесполезный результат.
- [ ] `scripts/visualize_graph.py` сохраняет `docs/agent-graph-custom.mmd` и `docs/agent-graph-prebuilt.mmd` . Файлы открываются в mermaid.live и совпадают с кодом сборки.
- [ ] `scripts/bench_agents.py` прогоняет 5 задач × 3 реализации × минимум 3 повтора, записывает результат в `docs/agent-graph-report.md` в виде таблицы. Latency и token usage — конкретные числа, не «стало быстрее».
- [ ] В `docs/agent-graph-report.md` есть Mermaid-схема (раздел 4) и явный вывод про custom vs prebuilt (раздел 6) с опорой на собственные числа.
- [ ] В отчёте описан минимум один реальный баг отладки (раздел 7) — без него видно, что код скопирован из туториала.

## Стартер-код (опционально)
Скелет `app/services/agent_graph.py` :

```python
import operator
from typing import Annotated, Literal, TypedDict
from langchain_core.messages import AnyMessage, ToolMessage
from langchain_core.tools import tool
from langchain_openai import ChatOpenAI
from langgraph.graph import END, START, StateGraph
from langgraph.graph.message import add_messages

# 1. Tools (переносятся из ДЗ Б6.2)
@tool
def multiply(a: int, b: int) -> int:
    """Перемножает два целых числа. Вызывать для любого умножения."""
    return a * b

@tool
def search_knowledge_base(query: str) -> str:
    """Ищет ответ в базе знаний по текстовому запросу."""
    # заглушка: подключить RAG из M5 либо вернуть 2–3 фейковых документа
    return f"Топ-результаты по запросу '{query}': ..."

TOOLS = [multiply, search_knowledge_base] # + доменный tool под тему диплома
MAX_ITERATIONS = 6

model = ChatOpenAI(model="gpt-5.4-mini", temperature=0).bind_tools(TOOLS)

# 2. State
class AgentState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]
    iteration_count: int
    tool_results: Annotated[list[dict], operator.add]

# 3. Nodes
async def call_model(state: AgentState) -> dict:
    response = await model.ainvoke(state["messages"])
    return {"messages": [response], "iteration_count": state["iteration_count"] + 1}

async def execute_tool(state: AgentState) -> dict:
    last = state["messages"][-1]
    by_name = {t.name: t for t in TOOLS}
    new_messages, new_results = [], []
    for tc in last.tool_calls:
        if tc["name"] not in by_name:
            content = f"error: unknown tool '{tc['name']}'"
        else:
            content = str(await by_name[tc["name"]].ainvoke(tc["args"]))
        new_messages.append(ToolMessage(content=content, tool_call_id=tc["id"]))
        new_results.append({"name": tc["name"], "args": tc["args"], "result": content})
    return {"messages": new_messages, "tool_results": new_results}

async def force_finish(state: AgentState) -> dict:
    return {} # последний AIMessage уже в state, прокидываем как есть

# 4. Router
def route_after_model(state: AgentState) -> Literal["execute_tool", "force_finish"]:
    if state["iteration_count"] >= MAX_ITERATIONS:
        return "force_finish"
    last = state["messages"][-1]
    return "execute_tool" if getattr(last, "tool_calls", None) else "force_finish"

# 5. Сборка
builder = StateGraph(AgentState)
builder.add_node("call_model", call_model)
builder.add_node("execute_tool", execute_tool)
builder.add_node("force_finish", force_finish)

builder.add_edge(START, "call_model")
builder.add_conditional_edges(
    "call_model", route_after_model,
    {"execute_tool": "execute_tool", "force_finish": "force_finish"},
)
builder.add_edge("execute_tool", "call_model")
builder.add_edge("force_finish", END)

custom_graph = builder.compile()

# 6. Prebuilt — для сравнения
from langchain.agents import create_agent # в LangChain 1.0 рекомендуемый путь

prebuilt_graph = create_agent(
    model="openai:gpt-5.4-mini",
    tools=TOOLS,
    system_prompt="Помоги решать задачи. Используй tools при необходимости.",
)
```
