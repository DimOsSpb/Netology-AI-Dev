# Решение

## Шаг 1. Компоненты гибридного сервиса

| Компонент | Роль в сервисе | Риск при отсутствии | Артефакт или проверка |
|-----------|----------------|---------------------|------------------------|
| **DVC** | Контроль версий данных и воспроизводимость пайплайна обучения. Гарантирует, что данные для обучения и метрики привязаны к конкретному состоянию кода и параметров. | Невозможность повторить обучение с теми же данными и параметрами; дрейф данных из-за незаметных изменений в train.csv. | `dvc.lock` (хеши данных и артефактов), `params.yaml` (параметры обучения), `metrics.json` (метрики). |
| **MLflow** | Трекинг экспериментов и реестр моделей. Хранит версии моделей, метрики обучения и алиасы (`production`, `staging`) для управления жизненным циклом. | Непонятное происхождение модели в продакшене; невозможность откатиться к предыдущей версии; отсутствие аудита изменений. | Модель в реестре (`models:/credit-model@production`), метрики в `runs/`, алиасы через `set_registered_model_alias`. |
| **FastAPI** | Веб-интерфейс для предсказаний. Валидирует входные данные, управляет кэшированием моделей по алиасам, предоставляет эндпоинты `/health` и `/predict`. | Нестабильный интерфейс для клиентов; отсутствие валидации приводит к ошибкам в продакшене; невозможность проверить доступность сервиса. | Эндпоинты `/health` и `/predict`, валидация через Pydantic, кэш моделей в памяти. |
| **Docker** | Контейнеризация приложения. Гарантирует идентичность окружения между разработкой, тестированием и продакшеном. | Различия в зависимостях Python, версиях библиотек между окружениями; «у меня на машине работало». | `Dockerfile`, образ `ml-service:<tag>`, smoke-тесты в CI. |
| **CI** | Автоматизация проверок перед релизом: обучение, дрифт-гейт, сборка Docker, smoke-тесты, публикация артефактов. | Ручные ошибки при деплое; пропуск критических проверок (дрейф, метрики); отсутствие верификации образа перед продакшеном. | GitHub Actions workflow, артефакты (`release_manifest.json`, `drift_report.html`), лог CI. |
| **Evidently** | ML-мониторинг дрифта данных в продакшене. Сравнивает распределение входных данных с референсом и блокирует деплой при превышении порога. | Незаметный дрейф данных, приводящий к деградации качества предсказаний; отсутствие сигналов о проблемах до падения метрик. | `monitor.py` (дрейфт-гейт), `drift_report.html`, метрика `drifted_share` в CI. |

## Шаг 2. Сравнение двух слоёв мониторинга

| Слой | Что наблюдаем | Пример сигнала | Действие команды |
|------|---------------|----------------|------------------|
| **Технический мониторинг** | Задержка ответа, HTTP-ошибки, использование CPU/RAM, статус `readiness`. | `curl -f localhost:8000/health` возвращает 503; CPU > 90%; время ответа > 5000 мс. | Перезапуск контейнера, масштабирование, проверка логов приложения, откат образа. |
| **ML-мониторинг** | Дрифт входных данных, распределение прогнозов, качество предсказаний (ROC-AUC, точность). | `drifted_share = 0.25` > порог 0.20; ROC-AUC упал с 0.90 до 0.75. | Блокировка деплоя через drift gate, запуск переобучения, анализ причин дрейфа, обновление модели. |

**Почему один слой не заменяет другой:**  
Технический мониторинг говорит о том, *работает ли сервис*, но не о том, *правильно ли он предсказывает*. ML-мониторинг видит деградацию качества, но не обнаружит падение сервиса из-за OOM или сетевых проблем. Оба слоя нужны для полной наблюдаемости.

## Шаг 3. Связь компонентов в цепочке запроса

```
┌─────────────┐
│ Клиент      │ → POST /predict (features, alias="production")
└──────┬──────┘
       │
┌──────▼─────────────────────────────────────────────────────────────┐
│ FastAPI (app/main.py)                                              │
│ • Валидирует вход (Pydantic)                                       │
│ • Загружает модель из MLflow по алиасу (кэш в памяти)              │
│ • Вызывает predict(model, df)                                      │
└──────┬─────────────────────────────────────────────────────────────┘
       │
┌──────▼─────────────────────────────────────────────────────────────┐
│ MLflow Registry                                                    │
│ • Алиас "production" → версия модели                               │
│ • Загрузка модели (mlflow.pyfunc.load_model)                       │
└──────┬─────────────────────────────────────────────────────────────┘
       │
┌──────▼─────────────────────────────────────────────────────────────┐
│ Модель (models/model.pkl)                                          │
│ • Обучена через DVC пайплайн (dvc.yaml)                            │
│ • Параметры зафиксированы в params.yaml                             │
│ • Данные в data/train.csv (dvc.lock)                               │
│ • Метрики: roc_auc = 0.90 (metrics.json)                           │
└──────┬─────────────────────────────────────────────────────────────┘
       │
┌──────▼─────────────────────────────────────────────────────────────┐
│ Ответ: {"prediction": 0.82, "model_alias": "production"}           │
└──────┬─────────────────────────────────────────────────────────────┘
       │
┌──────▼─────────────────────────────────────────────────────────────┐
│ CI / Evidently (мониторинг)                                        │
│ • DVC: проверяет целостность данных и параметров                   │
│ • MLflow: отслеживает метрики и версии                             │
│ • Evidently: сравнивает production_batch.csv с train.csv           │
│ • CI: smoke-тесты, release_manifest.json                           │
└────────────────────────────────────────────────────────────────────┘
```

**Пояснение:**  
1. Клиент отправляет запрос в FastAPI с признаками и алиасом модели.  
2. FastAPI валидирует вход и загружает модель из MLflow по алиасу `production`.  
3. Модель была обучена через DVC-пайплайн с зафиксированными данными, параметрами и метриками.  
4. После каждого деплоя CI проверяет дрифт через Evidently, собирает `release_manifest.json` и публикует образ в registry.  
5. Все компоненты связаны: DVC обеспечивает воспроизводимость, MLflow — управление версиями, FastAPI — доступность, Docker — идентичность окружения, CI — автоматизацию, Evidently — наблюдаемость.

## Ключевые артефакты проекта

| Артефакт | Описание |
|----------|----------|
| `dvc.yaml` | Пайплайн обучения с зависимостями от данных и параметров |
| `dvc.lock` | Хеши данных и артефактов для воспроизводимости |
| `params.yaml` | Параметры модели (n_estimators, max_depth) |
| `metrics.json` | Метрики обучения (roc_auc: 0.90) |
| `models/model.pkl` | Обученная модель |
| `app/main.py` | FastAPI с эндпоинтами и кэшированием моделей |
| `Dockerfile` | Контейнеризация приложения |
| `.github/workflows/ci.yml` | CI/CD workflow с обучением, дрифт-гейтом, smoke-тестами |
| `monitor.py` | Evidently drift gate с проверкой порога дрифта |
| `scripts/build_release_manifest.py` | Генерация release passport |

## Выводы

Гибридный сервис прогноза оттока представляет собой связную систему, где каждый компонент отвечает за свой аспект воспроизводимости, доступности и наблюдаемости:

- **DVC** связывает данные, код и метрики через хеши, обеспечивая воспроизводимость обучения.  
- **MLflow** управляет жизненным циклом моделей с алиасами для безопасного перехода между версиями.  
- **FastAPI** предоставляет стабильный интерфейс с валидацией и кэшированием.  
- **Docker** гарантирует идентичность окружения между этапами разработки и продакшена.  
- **CI** автоматизирует проверки перед релизом, включая дрифт-гейт и smoke-тесты.  
- **Evidently** мониторит дрифт данных в продакшене и блокирует деплой при превышении порога.

Отказ любого компонента ведёт к конкретным рискам: невозможности повторить обучение, неясному происхождению модели, нестабильному интерфейсу или незамеченному дрейфу данных.
