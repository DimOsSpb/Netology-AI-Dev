Домашнее задание: докажите воспроизводимость изменения
Информация о задании
Форма проверки: задание с самопроверкой
Цели задания: научиться связывать изменение параметра с пересчётом DVC-пайплайна, конкретным запуском MLflow, паспортом релиза и проверками CI.
Правила приёма работы: отправьте отчёт со скриншотами или фрагментами вывода команд и ссылкой на облачный документ. Не добавляйте remote-секреты, реальные токены и другие учётные данные.
Описание задания
Измените один параметр в params.yaml, воспроизведите pipeline, найдите созданный запуск модели и соберите паспорт релиза. В конце объясните, почему workflow проекта является CI, а не CD.
Шаг 1. Зафиксируйте изменение параметра.
Инструкция. Откройте учебный репозиторий и убедитесь, что зависимости установлены. Зафиксируйте текущий Git SHA командой git rev-parse --short HEAD. Затем в params.yaml выберите один параметр, используемый pipeline: сохраните его значение до изменения, измените только его и сохраните файл. Не меняйте одновременно код, данные и другие параметры — иначе нельзя будет доказать причину пересчёта.
Результат. Фрагмент params.yaml со старым и новым значением, Git SHA и короткое пояснение влияния параметра.
Шаг 2. Воспроизведите pipeline через DVC.
Инструкция. Выполните dvc repro и сохраните вывод, в котором видно, какие этапы пересчитаны. Затем выполните dvc status; при наличии метрик — dvc metrics show. Объясните причинную цепочку: изменённый параметр в params.yaml используется в dvc.yaml, а dvc.lock фиксирует обновлённые зависимости и результаты.
Результат. Скриншот или фрагмент вывода dvc repro и dvc status (при наличии — metrics show) с пояснением в 3–5 предложениях.
Шаг 3. Найдите запуск модели в MLflow.
Инструкция. После dvc repro откройте MLflow. Найдите run, созданный после изменения, по времени запуска или по параметру. Выпишите run ID, ключевые параметры и метрики. Сверьте, что этот run ID указан в model_metadata.json либо в другом метаданном артефакте модели, если он предусмотрен проектом.
Результат. Скриншот MLflow или выписка: run ID, параметры, метрики и связь с артефактом модели.
Шаг 4. Соберите паспорт релиза.
Инструкция. Запустите команду формирования паспорта, предусмотренную проектом (например, build_release_manifest.py). Откройте reports/release_manifest.json и убедитесь, что в нём связаны Git SHA, dvc.lock, данные, модель/MLflow run и тег Docker-образа. Отметьте, какие поля изменились вслед за параметром.
Результат. Фрагмент release_manifest.json и краткая расшифровка ключевых полей.
Шаг 5. Объясните границу CI и CD.
Инструкция. Прочитайте workflow GitHub Actions. Перечислите проверки, которые он выполняет: воспроизведение pipeline, формирование паспорта, тесты, Docker build и сохранение артефактов. Затем объясните, почему это CI: workflow не публикует образ и не развёртывает сервис. В конце соберите отчёт в цепочке «параметр → DVC → MLflow → паспорт релиза → CI/CD» и подпишите каждый скриншот.
Результат. Сравнение CI и CD на примере workflow проекта и ссылка на полный отчёт.
Критерии оценки
Критерии оценки
Изменён ровно один релевантный параметр; значения до и после зафиксированы, влияние объяснено.
DVC-след подтверждён: приведены пересчитанные/актуальные этапы и связь params.yaml → dvc.yaml → dvc.lock.
Указан новый MLflow run ID, параметры и метрики; показана связь с артефактом модели.
Паспорт релиза связывает Git, DVC lock, данные, модель/MLflow run и Docker-образ; секреты отсутствуют.
CI и CD различены корректно: указано отсутствие публикации образа и развёртывания.
Важно: используйте ИИ как помощника для черновиков и пояснений, но проверяйте команды, артефакты и выводы самостоятельно.
