# Блок 5.5 — Корпоративный RAG-ассистент

## Что делаем

Это основная сборка — корпоративный RAG-ассистент под свой дипломный проект. Берётся всё, что собрано на ДЗ Б5.3 (минимальный RAG: SimpleDirectoryReader → SentenceSplitter → Qdrant → QueryEngine) и Б5.4 (лучшая стратегия chunking + re-ranker + подобранные параметры на 10+ документах). Здесь добавляются multi-format ingestion (PDF/DOCX/HTML/MD), metadata-обогащение из путей, multi-turn-диалог через condense_plus_context , честный ответ «не знаю», цитирование источников через CitationQueryEngine и стриминг.

## Задачи

1. Расширить scripts/ingest.py : поддержка минимум двух форматов из PDF (PyMuPDFReader), DOCX ( llama-index-readers-file или Unstructured), HTML (HTMLTagReader или Unstructured), Markdown (MarkdownReader). Если все доступны — отлично, включить все четыре.

2. Поднять реальную базу: не менее 30 документов из предметной области в data/<category>/... . Если документы недоступны напрямую — написать scripts/download_data.py , который их скачивает (Confluence-export, открытые регламенты, статьи в MD и т.п.). Зафиксировать число файлов, форматы и общий размер в docs/data_inventory.md .

3. Реализовать metadata-обогащение в app/services/ingestion.py : source (имя файла), created_at или last_modified (из stat файла), author (если есть в самом документе — например, в DOCX core properties), category из путей вида data/<category>/file.pdf , version если зашит в имени. Шумные технические поля исключаются из эмбеддинга через excluded_embed_metadata_keys .

4. Собрать IngestionPipeline с SimpleDocumentStore и DocstoreStrategy.UPSERTS , SentenceSplitter с параметрами из ДЗ Б5.4, OpenAIEmbedding (или Sentence Transformers — по выбору из Б5.1), QdrantVectorStore . Проверить, что повторный запуск ingest не дублирует чанки.

5. Реализовать query pipeline в app/services/rag.py : query → retrieval top_k=10 → опциональный re-ranking (re-ranker из Б5.4, top_n=5 ) → код-гард отказа по top_score до вызова LLM → генерация ответа с нумерованными цитатами [1] , [2] . Цитаты делаются нумерованным контекстом + промптом с инструкцией цитировать (как в reference-сервисе) либо встроенным CitationQueryEngine — на выбор; обе техники дают [1] , [2] в тексте. Ответ — sources в JSON с полями id , file_name , page , score , snippet и флаг confident (из top_score ).

6. Multi-turn: история диалога уже лежит в Postgres из M4 ( ChatService , окно по токен-бюджету) — второй store заводить не нужно. Для генерации история уходит в LLM целиком, поэтому «а для них?» модель понимает из контекста — мультитёрн работает и так. Шаг condense опционален и чинит только поиск: вектор-поиск видит одну строку, и на коротких follow-up она бессмысленна. Если включается — один вызов LLM переписывает follow-up в самодостаточный вопрос с учётом окна истории, и уже его получает retrieval (ключ — chat_id ). Проверить, что ассистент корректно отвечает на «а для них?» после первого вопроса.

7. Ответ «не знаю»: добавить в системный промпт правило «отвечай только по контексту, при отсутствии — пиши “по базе не нашёл, могу эскалировать”». Реализовать score-guard: если max(score) < SCORE_THRESHOLD — LLM-вызов пропускается и сразу отдаётся готовое сообщение. Это двухслойная защита: код + промпт. Значение threshold берётся из конфига ( rag_score_threshold , по умолчанию 0.3 для cosine на OpenAI 3-small); на других embedding-моделях оно другое. Главное — обосновать выбор в docs/rag.md со ссылкой на распределение score на корпусе (golden из Б5.6 поможет откалибровать точнее).

8. Одношаговый ответ — на существующем POST /rag/query (из Б5.3), расширенном цитатами и confident (обязательно). Диалоговый стриминг — на POST /chats/{id}/messages из M4, где SSE уже реализован (опционально для ДЗ-самост, обязательно для финального чекпоинта 5): текст data: -событиями токен-за-токеном с sanitize-функцией для \n внутри chunk (см. слайд «Стриминг: добавляем источники в существующий SSE»), источники — финальным event: sources . Ручка загрузки POST /documents/upload принимает UploadFile , сохраняет в data/ , запускает IngestionPipeline.run через BackgroundTasks ( status_code=202 ). Для инкрементальной индексации используется DocstoreStrategy.UPSERTS .

9. Подключить RAG к Telegram-боту из M4: на текстовое сообщение бот зовёт /chats/{id}/messages (SSE), ответ собирает по чанкам и обновляет сообщение через editMessageText с дросселированием (раз в 700–1000 мс). Telegram-лимит на editMessageText — около 30 в секунду на чат, а bot API на одно и то же сообщение чаще ~1 раза в секунду рекомендует не вызывать; быстрее → 429 Too Many Requests. Реализовать debounce: хранится last_edit_at для каждого chat_id , сообщение обновляется только если прошло ≥ 700 мс с предыдущего edit (можно собрать через asyncio.Event или просто time.monotonic() ). Базовая механика стриминга через editMessageText уже разбиралась в M4Б3 — оттуда переносится debounce и логика обновления. После финального чанка прикрепляются inline-кнопки 👍/👎 (реюз механики M4Б4), которые шлют POST /chats/{id}/messages/{mid}/feedback со значением up / down и списком показанных sources .

10. docker-compose.yml поднимает целый стек одной командой docker compose up -d : app (FastAPI), qdrant , redis , bot . Никаких ручных шагов — только cp .env.example .env и заполнить ключи.

11. Обновить docs/rag.md : Mermaid-диаграмма архитектуры (два контура — ingestion и query), параметры chunking из Б5.4 (если Б5.4 пропущен — использовать дефолты chunk_size=512, chunk_overlap=64 , это и есть baseline со слайда «Chunking: первая развилка ingestion» из Б5.3), выбранный re-ranker, threshold для refusal с обоснованием, перечень endpoints.

## Критерии самопроверки

python scripts/ingest.py data/ индексирует 50+ документов разных форматов без ошибок, упавшие файлы переименованы в .failed и видны в логах.

Повторный запуск scripts/ingest.py data/ показывает «0 changed, N unchanged» (UPSERTS работает через docstore).

POST /rag/query работает синхронно (обязательно); диалоговый POST /chats/{id}/messages стримит ответ по SSE с sanitize для \n (обязательно для финального чекпоинта 5; для ДЗ-самост — опционально). В финальном event: sources есть массив с file_name , page , score , snippet .

Multi-turn: «Каков срок возврата?» → «А для электроники?» — второй ответ корректно учитывает контекст первого (проверено хотя бы на 1 явной паре).

Запрос про то, чего нет в базе, возвращает «по базе не нашёл, могу эскалировать», без галлюцинации; в логах видно срабатывание score-guard.

POST /documents/upload с PDF возвращает 202 , через 30–60 секунд новый документ появляется в индексе и доступен в ответах.

Telegram-бот отвечает через RAG (через /chats/{id}/messages ), сообщение обновляется по мере генерации, кнопки 👍/👎 сохраняют feedback.

docker compose up -d поднимает app + qdrant + redis + bot , ни одного docker exec или pip install руками.

docs/rag.md содержит Mermaid-диаграмму, параметры chunking, выбранный threshold с пояснением.

docs/data_inventory.md фиксирует число документов, разбивку по форматам и общий размер корпуса.

## Стартер-код

Не нужен. Работа продолжается в репозитории после ДЗ блока 5.4: к этому моменту уже есть Qdrant в docker-compose , базовый IngestionPipeline , выбранная стратегия chunking и re-ranker. На Б5.5 это масштабируется до полной сборки.

## Референсы

- LlamaIndex Data Connectors / file readers — SimpleDirectoryReader , PyMuPDFReader , DocxReader , HTMLTagReader .
- IngestionPipeline + DocstoreStrategy — UPSERTS и инкрементальная индексация.
- CitationQueryEngine — цитаты [1] , [2] и source_nodes .
- Chat Engine — condense_plus_context — multi-turn с rewrite.
- LlamaIndex Streaming — streaming=True + response_gen .
- PyMuPDF docs — канонический импорт import pymupdf (1.24+).
- Unstructured partitioning — для сложных PDF/DOCX, когда базовых ридеров не хватает.
- FastAPI BackgroundTasks — асинхронная индексация без блокировки запроса.
- Qdrant + LlamaIndex — QdrantVectorStore , hybrid search, фильтрация по metadata.
